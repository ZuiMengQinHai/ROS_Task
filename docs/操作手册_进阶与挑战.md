## 2. 【进阶 任务 1】一键启动 `integrated.launch.py`

**终端 A：**

```bash
ros2 launch tb3_tools integrated.launch.py
```

**应该看到**（日志顺序）：

1. `[tb3_tools] 进阶版顶层 Launch 已启动：TURTLEBOT3_MODEL=waffle_pi，use_sim_time=True，sim=True，enable_tf=True，window_sec=5.0，image_topic=/camera/image_raw，target_frame=moving_target`
2. 上游仿真拉起：`gazebo-1`(gz server)、`gazebo-2`(gz client)、`create-3`、`parameter_bridge-4`、`image_bridge-5`、`robot_state_publisher-6`
3. 自己 5 个节点：`image_monitor-7`、`static_tf_broadcaster-8`、`dynamic_tf_broadcaster-9`、`tf_listener-10`、`rviz2-11`
4. `image_monitor` 打印：`image_monitor 启动：统计窗口 window_sec=5.0s，发布周期 1.0s，输出话题 /image_monitor/fps（std_msgs/Float64）`
5. `static_tf_broadcaster` 打印：`静态 tf 已发布（/tf_static，transient_local）：base_link → inspection_point，平移 [0.150, 0.000, 0.200]`
6. `dynamic_tf_broadcaster` 每 8 s 打印一次 `moving_target 位置（odom 系）：x=+1.20 y=+0.05 z=+0.30，仿真时刻 0.1s`
7. `tf_listener` 每 ~5 s 打印 `moving_target 相对 base_link：… → 距离 1.235 m`
8. 弹出 **Gazebo 窗口**（Waffle Pi 在 world 里）和 **RViz 窗口**（`integrated.rviz`）

**参数一览**（`ros2 launch tb3_tools integrated.launch.py --show-args` 可查）：

| 参数 | 默认值 | 作用 |
| --- | --- | --- |
| `window_sec` | `5.0` | 图像监测的统计窗口长度（**进阶版要求用 Launch 参数控制**） |
| `image_topic` | `/camera/image_raw` | 图像监测节点的**重映射目标**（节点源码里只写相对名 `image`） |
| `target_frame` | `moving_target` | tf 监听要查询的目标坐标系 |
| `sim` | `true` | 是否包含 Gazebo；离线回放时 `false` |
| `enable_tf` | `true` | 是否启动自编静态/动态广播器；**离线回放时必须 `false`** |
| `use_sim_time` | `true` | 用 `/clock` 仿真时间（仿真和 bag 回放都要 true） |
| `rviz_config` | 本包 `rviz/integrated.rviz` | RViz 配置，用 `get_package_share_directory` 解析，**不写死路径** |
| `headless` | `false` | `true` 时只起仿真与节点，不弹 RViz |
| `x_pose` / `y_pose` | `-2.0` / `-0.5` | 小车初始位置 |

**常用变体：**

```bash
ros2 launch tb3_tools integrated.launch.py window_sec:=2.0      # 改统计窗口
ros2 launch tb3_tools integrated.launch.py headless:=true       # 不弹 RViz
ros2 launch tb3_tools integrated.launch.py image_topic:=/scan   # 改重映射（错误示范，见 3.4）
```

**怎么正确停**（⚠️ 实测坑）：

```bash
# 在终端 A 按 Ctrl+C 是最干净的；如果已经用 kill 杀掉过 Launch，一定要补这一刀，
# 否则自编节点会变成孤儿进程继续发 /tf、/image_monitor/fps，
# 后面再启动就会出现「同一个话题有两个发布者」，数据全乱：
pkill -f 'ros2 launch tb3_tools'; sleep 2
pkill -f 'tb3_tools/lib/tb3_tools'; pkill -f rviz2; pkill -f rqt
ps -ef | grep -E 'tb3_tools/lib|gz sim|rviz2|rqt_' | grep -v grep    # 应无输出
```

## 3. 【进阶 任务 2】图像帧率监测 + rqt Plot

### 3.1 看数值

**终端 B**（先做第 1 节的三件事）：

```bash
ros2 topic info /image_monitor/fps -v      # 类型 std_msgs/msg/Float64，发布者是 /image_monitor
ros2 topic echo /image_monitor/fps
```

**应看到** 大约每（仿真）秒一个值，实测在 **5 ～ 11** 之间（软件渲染下相机不是满 30 fps）。
日志里每 5 s 也有一行：`窗口 5.0s 内 40 帧 → 8.15 fps（累计 40 帧）`。

### 3.2 改统计窗口（参数验证）

```bash
ros2 param get /image_monitor window_sec          # 5.0
ros2 launch tb3_tools integrated.launch.py window_sec:=2.0    # 重新启动，日志里变成 2.0s
ros2 param get /image_monitor window_sec          # 2.0（另开终端查）
```

窗口变小 → 同一条曲线抖动更大、对突发丢帧更敏感；窗口变大 → 曲线更平滑但反应更慢。
这就是「参数确实生效」的证据。

> ⚠️ **实测坑（参数优先级）**：`Node(parameters=[参数文件, {字典}])` 里的字典会被
> launch_ros 写成 **`/**` 通配符段落**的临时参数文件；如果 `params.yaml` 里
> **按节点名**的段落（`image_monitor:`）也写了同名参数，它的优先级更高，覆盖就失效
> ——现象是 `window_sec` 一直停在 5.0，挑战版的坐标故障也注不进去。
>
> 本工程的处理：`params.yaml` 里**不写** `window_sec` 与 `target_frame`
> （默认值只留在节点代码里：5.0 / `moving_target`），这两个值只由 Launch 传，
> 于是通配符段落成了唯一来源，覆盖必然生效。
>
> ```bash
> ros2 param get /image_monitor window_sec   # window_sec:=2.0 启动后应为 2.0
> ros2 param get /tf_listener target_frame   # fault_mode:=frame 启动后应为 moving_target_fault
> ```

### 3.3 rqt Plot 画曲线

```bash
ros2 run rqt_plot rqt_plot /image_monitor/fps/data /tf_listener/distance/data
```

> 注意：rqt_plot 要写到**字段级**（`Float64` 的字段名是 `data`），只写话题名不会出曲线。
> 如果命令行参数没被接住，就在窗口顶部的 `Topic` 输入框里手工输入 `/image_monitor/fps/data` 回车。

### 3.4 改话题重映射（重映射验证）

```bash
# 1) 故意不改：节点源码里的相对名 image 会落到 /image（没人发布）
ros2 run tb3_tools image_monitor --ros-args -p use_sim_time:=false
#    另开终端：能看到订阅挂在 /image 上，且日志报「没有收到图像」
ros2 topic info -v /image

# 2) 加上重映射：订阅挂到 /camera/image_raw，帧率立刻有值
ros2 run tb3_tools image_monitor --ros-args -r image:=/camera/image_raw -p use_sim_time:=false
ros2 topic info -v /camera/image_raw | grep -A3 image_monitor
```

`ros2 launch tb3_tools integrated.launch.py image_topic:=/camera/image_missing`
则等于把监测节点接到一个**不存在**的话题上——这正是挑战版的「话题故障」，见第 8 节。

### 3.5 「画面正常但帧率曲线异常」要查什么

| 现象 | 先查什么 | 为什么 |
| --- | --- | --- |
| RViz/rqt 里画面正常，`/image_monitor/fps` 一直是 0 | `ros2 topic info -v /camera/image_raw` 看监测节点的订阅是否真挂在 `/camera/image_raw` | remap 没生效时节点订的是 `/image`，画面（RViz 直接订原话题）正常，监测却收不到 |
| 帧率忽高忽低、锯齿明显 | `ros2 topic hz /clock` 和 `ros2 param get /image_monitor window_sec` | 窗口太小 + 仿真时间步进不均匀；软件渲染下 RTF 只有 0.1 左右，墙钟和仿真时间差 10 倍 |
| 帧率长期低于相机名义帧率 | `ros2 topic bw /camera/image_raw`、查看 Gazebo 窗口帧率 | 图像桥接或渲染跟不上，属于算力问题，不是监测节点的 bug |
| 曲线中途掉到 0 又恢复 | 看 `ros2 topic hz /camera/image_raw` 是否断流 | 仿真暂停/卡顿、bag 回放到尾，都会让消息断流 |
| 数值是一次次的尖峰 | 确认 QoS：`ros2 topic info -v` 里监测节点是 `BEST_EFFORT` | 图像用 SensorData QoS，Best Effort 会丢帧，尖峰是正常抖动 |

## 4. 【进阶 任务 3】新增两组坐标系（静态 + 动态）

### 4.1 坐标系树

```bash
mkdir -p ~/task1_ws/docs/evidence && cd ~/task1_ws/docs/evidence
ros2 run tf2_tools view_frames
```

**应看到**（`frames_*.gv` / `.pdf`，或用 `dot -Tpng frames_*.gv -o tree.png` 转图）：

```
odom ──┬── base_footprint ── base_link ──┬── camera_link ── camera_rgb_frame ── camera_rgb_optical_frame
       │                                  ├── base_scan
       │                                  ├── imu_link
       │                                  ├── wheel_left_link / wheel_right_link / caster_*
       │                                  └── inspection_point        ← 本工程新增（静态）
       └── moving_target                                             ← 本工程新增（动态）
```

### 4.2 两组查询

```bash
ros2 run tf2_ros tf2_echo base_link inspection_point    # 静态：平移恒为 [0.150, 0.000, 0.200]
ros2 run tf2_ros tf2_echo odom moving_target            # 动态：位置在半径 1.2 m 的圆上转
ros2 run tf2_ros tf2_echo base_link moving_target       # 跨链：距离随目标位置变化
```

**判据（看时间戳和频率，这是最硬的判据）**：

| 关系 | 平移 | 时间戳 | 频率 | 结论 |
| --- | --- | --- | --- | --- |
| `base_link → inspection_point` | 恒定 `[0.15, 0, 0.20]` | 恒为 0 | 只发一次（`/tf_static`，transient_local） | **静态** |
| `odom → moving_target` | `x=1.2cos θ, y=1.2sin θ, z=0.3` | 持续推进 | 20 Hz（仿真时间） | **动态** |
| `odom → base_footprint` | 车不动时 `[0,0,0]`，一动就变 | 持续推进 | ~6 Hz（桥接给的） | **动态**（上游） |

为什么这样分工：

- 静态：机械安装位置**不随时间变化**，只需发布一次；走 `/tf_static`（transient_local）后，
  晚启动的 RViz / `tf2_echo` 也能拿到历史值，不占带宽、也不会让 TF 缓存重复告警。
- 动态：位姿随时间变化，**必须按频率持续广播**，接收端按时间戳插值；发一次就过期了。
- 命名避让：新 frame 叫 `inspection_point` / `moving_target`，与 `base_footprint`、`base_link`、
  `camera_link`、`camera_rgb_frame` 都不冲突；也没有重复广播已有的 `odom → base_footprint`。

### 4.3 RViz 里看

RViz 已加载 `integrated.rviz`，`TF` 显示项会自动画出所有 frame：
勾上 `Show Names` 后能看到 `inspection_point`（贴在车体前上方）和 `moving_target`（绕圈跑）。

## 5. 【进阶 任务 4】tf 监听与异常处理

```bash
ros2 topic echo /tf_listener/distance
```

**应看到** 持续输出 `data: 1.23…`（车在原点时约 1.24 m；目标绕圈，距离在 1.2 ～ 2.4 m 之间变化），
日志里每 5 s 一行 `moving_target 相对 base_link：x=+0.085 y=+1.477 z=-0.290 → 距离 1.507 m`。

**故意制造三种异常**（只改自己的配置，不动模型文件）：

```bash
# ① 坐标系不存在 → LookupException
ros2 launch tb3_tools integrated.launch.py target_frame:=moving_target_fault

# ② 坐标树不连通（把动态广播器关掉，目标帧就没人发）→ ConnectivityException / LookupException
ros2 launch tb3_tools integrated.launch.py enable_tf:=false

# ③ 时间戳对不上（回放时混用墙钟与仿真时间）→ ExtrapolationException
ros2 run tb3_tools tf_listener --ros-args -p use_sim_time:=false
```

**应该看到**：距离话题发布 `NaN`（rqt_plot 上表现为曲线**断开**而不是掉到 0），
并打印带排查建议的告警，例如：

```
[WARN] tf 查询失败 [LookupException]："moving_target_fault" passed to lookupTransform argument target_frame does not exist.
  处理建议：坐标系不存在或尚无数据：moving_target_fault / base_link；
  用 ros2 run tf2_tools view_frames 看树里有没有该 frame，用 ros2 run tf2_ros tf2_echo 单独确认
```

恢复正确配置后，日志会出现 `查询恢复正常（此前连续错误 N 次），当前距离 1.xxx m`。

> 设计要点：为什么发布 `NaN` 而不是 0？0 会被 rqt 画成一条真实的「距离=0」曲线，掩盖故障；
> NaN 在 rqt_plot 上是断线，肉眼立刻能看出「这段时间没数据」。

⚠️ **实测坑**：`rqt_graph` 在 `Nodes/Topics (active)` 模式下，如果还勾着
`Hide: Dead sinks` 和 `Hide: Leaf topics`，画布会**全白**（本工程的图像话题都是一对一的叶子话题）。
把这两个勾去掉就有图，或者把左上角模式换成 `Nodes only`。

以及 `/tf → tf_listener`、`/tf_listener/distance`；rqt_plot 里要同时有帧率和距离两条曲线。

### 6.2 录制数据包（顺序很关键）

`/tf_static`、`/robot_description` 是 **transient_local** 话题，只发布一次，
**晚启动的录制器拿不到历史值**，所以必须「先开录制，再启动 Launch」：

```bash
# 终端 R
cd ~/task1_ws && mkdir -p bags
ros2 bag record -o bags/integrated /camera/image_raw /odom /tf /tf_static /clock

# 终端 A：再启动顶层 Launch
ros2 launch tb3_tools integrated.launch.py

# 终端 B：让小车动 10 s 以上（键盘或直接发速度）
ros2 run turtlebot3_teleop teleop_keyboard
# 或者（Jazzy 是 TwistStamped，别用旧版 Twist）
ros2 topic pub -r 10 /cmd_vel geometry_msgs/msg/TwistStamped \
  '{header: {frame_id: base_link}, twist: {linear: {x: 0.12}, angular: {z: 0.35}}}'

# 终端 R：Ctrl+C 停止录制，等它写完
```

⚠️ **实测坑**：`Ctrl+C` 后录制器要把缓存刷盘，**必须等它自己退出**（`Recording stopped`）。
如果这时直接 `kill -9`，`metadata.yaml` 写不出来，`ros2 bag info` 会报
`Could not find metadata in bag directory`，整包作废。

核对：

```bash
ros2 bag info bags/integrated
```

| Messages | 6955 |

| `/odom` | 297 |
| `/tf` | 533（含自己新增的 `odom → moving_target`） |
| `/tf_static` | 2（含 `base_link → inspection_point`） |

### 6.3 停掉仿真，只用 RViz + bag 回放

```bash
# 1) 确认 Gazebo 已停
pkill -f 'ros2 launch tb3_tools'; pkill -f 'gz sim'; sleep 3
ps -ef | grep -E 'gz sim|rviz2' | grep -v grep        # 应无输出

# 2) 只用 bag 提供输入：不起 Gazebo、不起自编 tf 广播器
ros2 launch tb3_tools bringup.launch.py mode:=offline start_rqt:=true

# 3) 另一个终端回放（--clock 必须有）
cd ~/task1_ws && ros2 bag play bags/integrated --clock
```

**预期**：RViz 的 Image 重新出画面、TF 重新出现（`moving_target` 又开始绕圈），
rqt_plot 的帧率曲线重新有值，`/tf_listener/distance` 重新出数值。
**不需要**让 Gazebo 里的小车重新动，因为 bag 存的是 ROS 消息流，不是仿真器状态。

**能复现 / 不能复现（任务书要求解释）**：

| 能靠 bag 复现 | 不能只靠 bag 复现 |
| --- | --- |
| 图像、`/odom`、`/tf`、`/tf_static` 这些**发过的话题** | Gazebo 的**物理世界状态**：小车真实位姿、碰撞、摩擦、正在施加的力 |
| 自己节点的**输入**，以及由此产生的**输出**（帧率曲线、距离曲线） | 没录的话题（本包没录 `/scan`、`/robot_description`，所以回放时 RViz 的激光与车模是空的） |
| 时间轴（`--clock` + `use_sim_time` 后与录制时一致） | 服务调用、参数变更历史、节点内部状态 |
| 故障的**现象**（话题无人发布、frame 不存在） | 现场的**因果**必然性：故障 2 在回放里也要靠配置注入才出现 |

## 8. 【挑战 任务 1】故障模式切换

用 `bringup.launch.py` 的两个参数切换：

```bash
ros2 launch tb3_tools bringup.launch.py                        # 正常（在线仿真）
ros2 launch tb3_tools bringup.launch.py fault_mode:=topic      # 话题故障
ros2 launch tb3_tools bringup.launch.py fault_mode:=frame      # 坐标故障
ros2 launch tb3_tools bringup.launch.py mode:=offline          # 离线：不起 Gazebo、不起自编 tf
```

| 故障 | 注入方式（只改本包配置） | 预期现象 |
| --- | --- | --- |
| `topic` | 监测节点的相对话题 `image` 重映射到 `/camera/image_missing`（无人发布） | `/image_monitor/fps` 恒 0；`/camera/image_missing` 只有订阅者没有发布者；日志反复告警「已 3.0s 以上没有收到图像」；**RViz 里的图像仍然正常**（RViz 直接订 `/camera/image_raw`） |
| `frame` | 监听节点的 `target_frame` 改成 `moving_target_fault`（树里不存在） | `/tf_listener/distance` 发布 NaN，曲线断开；日志报 `LookupException`；`view_frames` 里没有该 frame；RViz 的 TF 里也找不到 |

修复动作就是把参数改回默认（`fault_mode:=none`），不需要改代码、不需要动 ROBOTIS 的模型文件。

## 13. 常见问题（都是本次实测踩到的）

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 同一个话题出现两个发布者、数值乱跳 | 上一轮的节点没被杀死（`pkill -f 'ros2 launch'` 只杀启动器） | `pkill -f 'tb3_tools/lib/tb3_tools'`；`ros2 node list` 里同名节点出现多次就是这个问题 |
| `window_sec` 改了不生效 | Launch 里用参数字典覆盖，被写成 `/**` 通配符段落，优先级低于 `params.yaml` | 改用 `--ros-args -p window_sec:=…`（本工程已改），`ros2 param get` 核对 |
| rqt_graph 全白 | `Hide: Dead sinks` + `Hide: Leaf topics` 把叶子话题藏掉了 | 取消这两个勾，或切 `Nodes only` |
| rqt_plot 没曲线 | 只写话题名，没写到字段 | 用 `/image_monitor/fps/data`、`/tf_listener/distance/data` |
| `ros2 bag info` 报找不到 metadata | 录制器被 `kill -9`，元数据没写出来 | 用 Ctrl+C，等 `Recording stopped` 再动 |
| 回放时 RViz 空白 | 忘了 `--clock` 或 `use_sim_time:=false` | 见 6.3 |
| 回放时车模/激光没有 | 包里没录 `/robot_description`、`/scan` | 正常现象，见 6.3 的「不能复现」表 |
| 帧率/距离几秒才一个点 | 仿真 RTF 只有 ~0.1（软件渲染），仿真 1 s ≈ 墙钟 10 s | 用 `--rate 0.5` 回放，或把 `window_sec` 调小 |
| `ros2 topic echo -n 4` 报错 | Jazzy 的 `echo` 没有 `-n`（`-n` 是 `--no-arr`） | 用 `--once` 或 `timeout 10 ros2 topic echo …` |

## 15. 三个必答题（进阶/挑战角度补充）

**1. Gazebo、RViz 和 rqt 分别负责什么？**

> Gazebo 是**数据源**：产生 `/camera/image_raw`、`/odom`、`/scan`、`/tf`、`/clock`；
> RViz 是**场景化显示**：把 TF、激光、图像按保存好的配置一次画出来，适合交付和现场演示；
> rqt 是**调试台**：Node Graph 看「谁连了谁」，Plot 看数值随时间的变化，Image View 快速验证图像流。
> 进阶阶段三者分工更明确：问题多半先在 rqt 里被发现（曲线掉 0、连接错位），
> 再去 RViz 看几何是否对，最后回 Gazebo 查物理/传感器。

**2. `odom → base_footprint` 与 `base_link → camera_rgb_frame` 为什么一动态一静态？**

> 前者是里程计推算的**位姿**，车一动数值就变，必须按频率广播（本机 ~6 Hz），时间戳持续推进；
> 后者是 URDF 里相机的**安装位置**（本机 `base_link → camera_rgb_frame` 实测 `[0.076, 0.000, 0.093]`，
> 由 `camera_link`、`camera_rgb_frame` 两段固定关节叠加而成），
> 机械上固定不变，只发一次就够，走 `/tf_static`。本工程新增的
> `base_link → inspection_point` 同样是静态，`odom → moving_target` 同样是动态，
> 正好一对对照：`tf2_echo` 里一个时间戳恒 0，一个持续推进。

**3. rosbag 能回放什么，不能直接恢复什么？**

> 能回放当时**发布过的消息流**（图像、odom、tf、tf_static），所以只开 RViz 就能重现画面和坐标变换；
> 不能恢复 Gazebo 的**物理状态**（真实位姿、碰撞、力），也不能恢复没录的话题与服务调用。
> 挑战版的对照实验正好说明这一点：同一份 bag 能让「帧率曲线」和「距离曲线」重现（输入相同 → 输出相同），
> 但故障本身（话题名写错、frame 名写错）是**配置**带来的，必须靠 `fault_mode` 注入才出现，
> bag 里并没有「故障」这种东西。
