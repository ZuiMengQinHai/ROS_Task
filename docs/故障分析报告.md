# 故障分析报告（挑战版）

> 对应任务书 挑战版：两种可切换故障的「预期现象—诊断证据—根因—修复动作」四栏记录，
> 以及「同一份数据包跑正常/故障」的对照结论。
> 所有引用都对应 `docs/evidence/` 下的真实文件；命令均在虚拟机 `~/task1_ws` 下执行。

## 0. 复现环境与数据

| 项目 | 值 |
| --- | --- |
| 系统 / ROS | Ubuntu 24.04.5 LTS / ROS 2 Jazzy |
| 仿真 | Gazebo Sim 8.15（Harmonic），`turtlebot3_world.launch.py` |
| 模型 | TurtleBot3 **Waffle Pi**（`TURTLEBOT3_MODEL=waffle_pi`） |
| 数据包 | `bags/final`（回放用 `bags/integrated` 同名副本） |
| 包里话题 | `/camera/image_raw`、`/odom`、`/tf`、`/tf_static`、`/clock`、`/robot_description` |
| 录制顺序 | **先开录制，再启动 Launch**（否则 transient_local 的 `/tf_static`、`/robot_description` 抓不到） |
| 回放命令 | `ros2 bag play bags/final --clock --rate 0.5` |
| 回放时不启动 | Gazebo、自编静态/动态 tf 广播器（`mode:=offline` 已保证） |

故障入口（只作用于本包配置，不动 ROBOTIS 原始模型文件）：

```bash
ros2 launch tb3_tools bringup.launch.py mode:=offline fault_mode:=topic
ros2 launch tb3_tools bringup.launch.py mode:=offline fault_mode:=frame
```

## 1. 故障一：话题故障（监测节点重映射到不存在的图像话题）

| 栏目 | 内容 |
| --- | --- |
| **预期现象** | `/image_monitor/fps` 恒为 0；`/camera/image_missing` 只有订阅者、没有发布者；监测节点日志反复告警「已 3.0s 以上没有收到图像消息」；**RViz 的图像显示仍然正常**（RViz 直接订 `/camera/image_raw`） |
| **诊断证据** | ① `ros2 topic list -t`：出现 `/camera/image_missing [sensor_msgs/msg/Image]`，而 `/camera/image_raw` 同时存在<br>② `ros2 topic info -v /camera/image_missing`：`Publisher count: 0`、`Subscription count: 1`（订阅者是 `image_monitor`）<br>③ `ros2 param get /image_monitor window_sec` 正常（5.0），说明参数没问题，问题在**连接**上<br>④ `ros2 topic echo /image_monitor/fps` 只有 `data: 0.0`<br>⑤ rqt Node Graph：`/camera/image_missing → /image_monitor` 这条边悬空，没有发布端 |
| **根因** | Launch 把监测节点的相对话题名 `image` 重映射到了 `/camera/image_missing`（`fault_mode:=topic` 注入）。节点本身正常，只是**没有数据源**；RViz 与监测节点订阅的是两条不同话题，所以「画面正常但曲线为 0」 |
| **修复动作** | `fault_mode:=none`（把重映射改回 `/camera/image_raw`），或直接 `ros2 launch tb3_tools integrated.launch.py`。修复后 `ros2 topic info -v /camera/image_raw` 里能看到 `image_monitor` 的订阅，帧率恢复 |

## 2. 故障二：坐标故障（监听节点查询不存在的目标坐标系）

| 栏目 | 内容 |
| --- | --- |
| **预期现象** | `/tf_listener/distance` 发布 `NaN` → rqt_plot 上距离曲线**断开**（不是掉到 0）；日志报 `LookupException`；`view_frames` 的树里没有 `moving_target_fault`；`tf2_echo base_link moving_target_fault` 一直等待 |
| **诊断证据** | ① `ros2 param get /tf_listener target_frame` → **`moving_target_fault`**（先确认注入生效，见 `evidence/fix_param_check.txt`）<br>② 日志原文：`tf 查询失败 [LookupException]："moving_target_fault" passed to lookupTransform argument target_frame does not exist.`<br>③ `ros2 topic echo /tf_listener/distance` → `data: .nan`（正常配置同一条命令是 `data: 1.2345`）<br>④ `ros2 run tf2_tools view_frames` 导出的 `frames_*.gv` 里只有 `moving_target`，没有 `moving_target_fault`<br>⑤ `ros2 run tf2_ros tf2_echo base_link moving_target_fault` → `Invalid frame ID` 循环<br>⑥ 同一次运行里 `/image_monitor/fps` 仍能出值（故障只作用于坐标链路），说明不是「整体没数据」 |
| **根因** | `fault_mode:=frame` 把监听节点的 `target_frame` 改成 `moving_target_fault`，这个 frame 从来没有广播器发布，`lookup_transform` 在解析目标帧时就失败（**配置错误**，不是数据缺失） |
| **修复动作** | `fault_mode:=none`（`target_frame` 回到 `moving_target`）。修复后日志出现「查询恢复正常（此前连续错误 N 次），当前距离 1.2xx m」，曲线重新连起来 |

## 3. 同一份数据包的对照结果

同一份 `bags/final`、同样的回放命令（`--clock --rate 0.5`），只改 `fault_mode`：

| 观察项 | `fault_mode:=none` | `fault_mode:=topic` | `fault_mode:=frame` |
| --- | --- | --- | --- |
| `ros2 param get /tf_listener target_frame` | `moving_target` | `moving_target` | **`moving_target_fault`**（证明故障确实注入） |
| `/image_monitor/fps` 实测 | `10.10` | **`0.0`** | `10.10`（故障只作用于坐标，帧率不受影响） |
| `/tf_listener/distance` 实测 | `1.2345`（目标绕圈时变到 2.4 左右） | `1.2345`（正常） | **`.nan`**（rqt_plot 上曲线断开） |
| `/camera/image_missing` | 不存在 | **`Publisher count: 0` / `Subscription count: 1`（订阅者是 image_monitor）** | 不存在 |
| RViz 图像显示 | 有画面 | **有画面**（与监测节点无关，这正是「画面正常但曲线为 0」） | 有画面 |
| `view_frames` | 含 `inspection_point`、`moving_target` | 同上 | 树里只有 `moving_target`，**没有** `moving_target_fault` |
| 节点日志 | 无 WARN | `已 3.0s 以上没有收到图像消息…` | `tf 查询失败 [LookupException]："moving_target_fault" … does not exist` |

结论：**同一份输入 + 不同配置 ⇒ 可复现地产生不同的可观测输出**，故障不是「随机现象」，而是配置决定的。

> 附一条真实踩坑记录：这一轮做对照时，`fault_mode:=frame` 一开始**没有复现**——
> 距离照常输出 1.234 m。查下来是 Launch 参数覆盖失效（`target_frame` 没被改掉），
> 见 `AI_协作记录.md` 记录一。修正后 `ros2 param get` 显示 `moving_target_fault`、
> 距离变 `.nan`，故障才真正可复现。这也说明**「故障没复现」本身就是一条诊断线索**：
> 先确认「注入是否生效」，再谈「现象是否出现」。

## 4. 哪些现象能靠 bag 重现，哪些不能

| 能重现 | 不能重现 |
| --- | --- |
| 图像、`/odom`、`/tf`、`/tf_static` 的消息流 | Gazebo 的物理状态（真实位姿、碰撞、摩擦、施加的力） |
| 由这些输入算出来的输出：帧率曲线、距离曲线 | 没录的话题（本包未录 `/scan`，因此回放时 RViz 的激光是空的） |
| 时间轴（`--clock` + `use_sim_time` 与录制时一致） | 服务调用、参数修改历史 |
| 故障的**可观测现象**（话题悬空、frame 缺失） | 故障的**成因**：故障是配置注入的，bag 里没有「故障」这种东西 |

> 这条正是任务书要求解释的点：bag 保存的是 ROS 消息流，不是仿真器状态；
> 所以「同样的输入 → 同样的输出」可以复现，而「物理世界」和「配置/因果」必须靠环境与 Launch 提供。
