# 进阶版说明（交付文档的「简短说明」）

> 对应任务书 进阶版「验收与提交」里要求的那份说明：
> 静态与动态广播各解决什么问题、参数与重映射各改了什么。
> 运行步骤见 `docs/操作手册_进阶与挑战.md`，证据见 `docs/evidence/`。

## 一、新增了什么

| 文件 | 一行说明 |
| --- | --- |
| `tb3_tools/image_monitor.py` | 订阅相机图像，按可配置时间窗口统计帧率，发布 `std_msgs/msg/Float64` |
| `tb3_tools/static_tf_broadcaster.py` | `base_link → inspection_point` 静态变换，走 `/tf_static` |
| `tb3_tools/dynamic_tf_broadcaster.py` | `odom → moving_target` 动态变换，8 s 一圈、半径 1.2 m、z=0.3 m |
| `tb3_tools/tf_listener.py` | 查询 `base_link → moving_target` 距离，分别处理 3 类 tf2 异常 |
| `launch/integrated.launch.py` | 顶层 Launch：包含仿真 + 4 个自编节点 + RViz |
| `rviz/integrated.rviz` | Fixed Frame `odom`、TF / LaserScan / Image 显示项 |
| `config/params.yaml` | 各节点参数默认值 |

## 二、静态广播 vs 动态广播，各解决什么问题

| | 静态广播器 | 动态广播器 |
| --- | --- | --- |
| 本工程的例子 | `base_link → inspection_point` | `odom → moving_target` |
| 解决的问题 | 「车体上**固定不动**的一个点在哪」——机械安装位置，与时间无关 | 「一个**随时间运动**的目标此刻在哪」——必须持续刷新 |
| 实现方式 | `tf2_ros.StaticTransformBroadcaster`，启动时发一次 | `tf2_ros.TransformBroadcaster` + 20 Hz 定时器 |
| 走哪个话题 | `/tf_static`（transient_local，晚来的订阅者也能拿到） | `/tf`（volatile，只对当下有效） |
| 时间戳 | 0（或发布时刻），之后不再变 | 每个周期取节点时钟（仿真时间）的新值 |
| 为什么不能互换 | 用动态方式发静态变换会 20 Hz 重复一份不变的数据，白白占带宽，还会让 TF 缓存出现重复数据告警 | 用静态方式发动态变换，接收端永远只看到第一帧，坐标不会跟着动 |

两者的接收侧是完全一致的：`tf2_echo`、`view_frames`、RViz 的 TF 显示项都同时读 `/tf` 与 `/tf_static`，
所以在本工程里它们出现在**同一棵树**上（`odom` 下挂着 `base_footprint` 和 `moving_target`，
`base_link` 下挂着 `inspection_point` 与原有的 `camera_link`/`base_scan`/轮子等）。

命名避让：新增 frame 叫 `inspection_point`、`moving_target`，与 `base_footprint`、`base_link`、
`camera_link`、`camera_rgb_frame`、`base_scan`、`imu_link`、`wheel_*` 均不冲突；
也没有重复广播上游已有的 `odom → base_footprint`（那是 `ros_gz_bridge` 的职责）。

## 三、参数改了什么

| 参数 | 默认 | 谁读 | 改它会发生什么 |
| --- | --- | --- | --- |
| `window_sec` | 5.0 | `image_monitor` | 改变帧率统计窗口：变小→曲线抖动大、反应快；变大→平滑但滞后 |
| `publish_period_sec` | 1.0 | `image_monitor` | 数值话题发布周期（rqt_plot 的点密度） |
| `fps_topic` | `~/fps` | `image_monitor` | 输出话题名（节点名 `image_monitor` → `/image_monitor/fps`） |
| `stale_warn_sec` | 3.0 | `image_monitor` | 多久没收到图像就告警（话题故障的诊断依据） |
| `parent_frame` / `child_frame` | `base_link` / `inspection_point` | 静态广播器 | 静态变换的两端 |
| `x,y,z,roll,pitch,yaw` | 0.15,0,0.20,0,0,0 | 静态广播器 | 检查点的位置姿态 |
| `period_sec` / `radius_m` / `z_m` | 8.0 / 1.2 / 0.3 | 动态广播器 | 目标转一圈的时间、半径、高度 |
| `publish_rate_hz` | 20.0 | 动态广播器 | 动态变换的广播频率 |
| `source_frame` / `target_frame` | `base_link` / `moving_target` | `tf_listener` | 查哪两帧之间的距离 |
| `lookup_period_sec` / `timeout_sec` | 0.2 / 0.2 | `tf_listener` | 查询频率与单次超时（超时走异常分支） |
| `distance_topic` | `/tf_listener/distance` | `tf_listener` | 距离输出话题 |

**参数覆盖的坑（本次实测）**：Launch 里如果写成
`Node(parameters=[params.yaml, {'window_sec': 2.0}])`，
launch_ros 会把那个字典写成 **`/**` 通配符段落**的临时参数文件；
如果 `params.yaml` 里 `image_monitor:` 段落下也写了 `window_sec`，
按节点名的段落优先级更高，覆盖就失效——现象是 `window_sec` 永远是 5.0，
挑战版的坐标故障（改 `target_frame`）也注不进去。
本工程的处理：`params.yaml` **不写** `window_sec` 与 `target_frame`，
只在节点代码里给默认值（5.0 / `moving_target`），这两个值只由 Launch 传，
于是通配符段落是唯一来源，覆盖必然生效。
核对：`ros2 param get /image_monitor window_sec`（应为 2.0）、
`ros2 param get /tf_listener target_frame`（故障时应为 `moving_target_fault`）。

## 四、重映射改了什么

节点源码里**不出现具体相机话题名**，只订阅相对名 `image`：

```python
self.create_subscription(Image, 'image', self._on_image, qos_profile_sensor_data)
```

由 Launch 决定它到底连到哪个话题：

```python
remappings=[('image', image_topic)]     # image_topic 默认 /camera/image_raw
```

| 用法 | 监测节点实际订阅 | 结果 |
| --- | --- | --- |
| 默认 `image_topic:=/camera/image_raw` | `/camera/image_raw` | 正常出帧率 |
| `image_topic:=/camera/image_missing` | `/camera/image_missing` | 帧率恒 0，日志告警——挑战版的「话题故障」 |
| 单独跑节点但不给 remap | `/image`（没人发布） | 同样 0，说明「不 remap 就不通」 |

好处是：换模型、换相机话题、注故障都只改 Launch 一处，节点代码一行不动，
而且 `rqt Node Graph` 上能直接看到 `image` 被解析到了哪条话题。
